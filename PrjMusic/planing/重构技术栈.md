# EchoMemory 重构技术栈方案

## 1. 现状分析

当前项目采用三模块分离架构：

| 模块 | 技术栈 | 代码行数 | 职责 |
|------|--------|----------|------|
| `echomusic` | Java Spring Boot + MyBatis Plus | ~13,213 | 核心业务后端 |
| `echovue` | Vue 3 + TypeScript + Vite | ~24,670 | 用户端前端 |
| `echoai` | Python FastAPI | ~3,322 | AI Agent 服务 |

### 1.1 痛点

- **Java 后端代码冗余**：Service 接口与 Impl 成对出现、DTO/VO/Entity 多层转换、XML/注解配置分散。
- **前端 API 层手工维护**：`echovue/src/api/` 下大量手写请求函数，与后端接口耦合紧密，变更时双向修改。
- **技术栈割裂**：后端同时使用 Java 和 Python，运维和开发上下文切换成本高。

## 2. 目标架构

将 `echomusic` 从 Java Spring Boot 迁移至 Python FastAPI，与 `echoai` 合并为统一 Python 后端；前端保留 Vue 3，通过工程化工具和自动化生成减少样板代码。

```
EchoMemory/
├── backend/                  # 统一 Python 后端（原 echomusic + echoai）
│   ├── app/
│   ├── alembic/              # 数据库迁移
│   └── tests/
├── frontend/                 # 保留 Vue 3（原 echovue）
│   ├── src/
│   ├── openapi/              # 自动生成的 API 客户端
│   └── tests/
└── sqls/                     # 数据库脚本（已有）
```

## 3. 后端技术选型

### 3.1 核心框架：FastAPI

沿用 `echoai` 已验证的技术栈，迁移 `echomusic` 的全部业务接口。

| 特性 | Spring Boot | FastAPI | 收益 |
|------|-------------|---------|------|
| 数据校验 | Bean Validation + 手写 | Pydantic 自动校验 | 减少 DTO/VO 类数量 |
| API 文档 | Swagger 注解 | 自动从类型生成 | 零额外代码 |
| 依赖注入 | `@Autowired` / 构造器 | 函数参数依赖 | 代码更扁平 |
| 异步支持 | WebFlux（学习曲线高） | 原生 async/await | IO 密集型场景性能更好 |

### 3.2 ORM：SQLAlchemy 2.0 + asyncpg

替换 MyBatis Plus。

- **SQLAlchemy 2.0** 引入 `Mapped[]` 类型注解语法，模型定义与 Pydantic schema 可以高度复用类型提示。
- **`asyncpg`** 作为 PostgreSQL 异步驱动，配合 FastAPI 的异步路由处理高并发请求（音乐流媒体的播放、搜索等场景）。
- 复杂查询仍可通过 `select()` / `joinedload()` 精确控制，不牺牲灵活性。

### 3.3 数据库迁移：Alembic

替换 MyBatis Plus 的迁移方案（如果有）或手工 SQL 管理。

- 与 SQLAlchemy 模型联动，`alembic revision --autogenerate` 可自动生成迁移脚本。
- 支持回滚 (`alembic downgrade`)，迁移历史可追溯。

### 3.4 认证：fastapi-users

替换 Spring Security + 手写 JWT 过滤器。

- 内置 JWT / OAuth2 / Cookie 策略。
- 自动处理注册、登录、密码重置、邮箱验证。
- 与 SQLAlchemy 模型直接集成，减少 `JwtAuthenticationFilter`、`SecurityConfig` 等数百行配置代码。

### 3.5 文件存储：保留现有 OSS 逻辑

当前使用阿里云 OSS，Python 侧替换为 `aliyun-python-sdk-oss` 或 `oss2`，逻辑迁移成本较低。

### 3.6 缓存与消息队列：保留 Redis

- 缓存：使用 `redis-py` 的异步客户端 `redis.asyncio`。
- 热点计算（原 `HotServiceImpl`）：可继续使用 Redis Sorted Set，或评估是否需要引入 Celery + Redis 做异步任务队列。

## 4. 前端技术选型（保留 Vue 3，增强工程化）

### 4.1 核心框架：Vue 3 + TypeScript + Vite

现有 `echovue` 技术栈保持不变，避免 24,000+ 行代码的无效迁移。

### 4.2 状态管理：Pinia

继续使用 Pinia（已在项目中）。如需进一步精简，可评估：

- 全局状态是否真的需要 Store，还是可以通过 Composable + `provide/inject` 解决。
- 当前 14 个视图模块若存在过度集中的 Store，可按模块拆分为独立 Composables。

### 4.3 新增工具 1：unplugin-auto-import

**作用**：自动导入 Vue / Vue Router / Pinia API，无需手写 `import { ref, computed } from 'vue'`。

**预期收益**：
- 减少 `echovue/src/` 下约 15%–20% 的 `import` 行数。
- 降低新文件创建的样板成本。

### 4.4 新增工具 2：unplugin-vue-components

**作用**：按目录自动注册 Vue 组件，无需 `import MyComponent from './components/MyComponent.vue'`。

**预期收益**：
- `views/` 下的页面组件引用更简洁。
- 组件改名时无需修改多处 import。

### 4.5 新增工具 3：OpenAPI 自动生成客户端

**核心改进**。FastAPI 启动后自动生成 `/openapi.json`，前端通过工具链将其转为 TypeScript 客户端代码。

| 工具 | 输出 | 适用场景 |
|------|------|----------|
| `openapi-typescript` | 原始类型定义 | 希望自己封装请求层 |
| `openapi-fetch` | 类型安全的 fetch 封装 | 轻量项目，不想引入重型生成器 |
| `openapi-generator-cli` | 完整 API 客户端类 | 接口多、需要完整封装 |

**建议选型**：`openapi-typescript` + `openapi-fetch`。

- `openapi-typescript` 将 `/openapi.json` 转为 `schema.ts`，包含所有接口的输入/输出类型。
- `openapi-fetch` 提供类型安全的请求函数，自动推断路径参数、Query、Body、Response 类型。
- 效果：删除 `echovue/src/api/` 下全部手写请求代码，后端接口变更后前端只需重新生成类型即可捕获类型错误。

### 4.6 代码规范：继续 ESLint + Prettier

已有配置保持不变，新增 `unplugin-auto-import` 的 `eslintrc` 自动生成，避免未定义变量误报。

## 6. 迁移策略概述

### 阶段 1：后端基架搭建

1. 新建 `backend/` 目录，初始化 FastAPI + SQLAlchemy 2.0 + Alembic。
2. 迁移数据库模型：将 Java Entity 翻译为 SQLAlchemy `Mapped` 模型。
3. 配置 `fastapi-users`，实现注册/登录/ JWT，替换 Spring Security。

### 阶段 2：接口逐个迁移

按优先级分批迁移 Controller：

1. **第一批**（认证 + 用户）：`UserController`、`Auth` 相关。
2. **第二批**（核心内容）：`MusicController`、`AlbumController`、`PlaylistController`。
3. **第三批**（社交/AI）：`CommentController`、`SpacePostController`、`AiAgentController`（合并 echoai）。
4. **第四批**（边缘功能）：`BannerController`、`PlayHistoryController` 等。

每批迁移后，前端通过 OpenAPI 生成新客户端并验证。

### 阶段 3：前端工程化增强

1. 接入 `unplugin-auto-import` + `unplugin-vue-components`。
2. 接入 `openapi-typescript`，逐步替换 `src/api/` 下的手写请求。
3. 删除废弃的 API 文件，清理类型定义。

### 阶段 4：测试与废弃

1. 集成测试覆盖所有核心接口。
2. 确认无误后，标记 `echomusic/` 和 `echoai/` 为废弃，最终删除。

## 7. 预期收益

| 指标 | 现状 | 目标 | 变化 |
|------|------|------|------|
| 后端代码行数 | ~13,213 | ~5,500–7,000 | **↓ 45%–58%** |
| 前端样板代码 | ~3,000（估算 api + imports） | ~500（自动生成） | **↓ 80%** |
| 技术栈种类 | Java + Python + JS/TS | Python + JS/TS | **减少一种后端语言** |
| API 文档维护 | 手写 Swagger 注解 | 零成本自动生成 | **维护成本归零** |
| 接口类型安全 | 无（手写 any/手动类型） | 端到端 TypeScript 类型推导 | **类型覆盖率提升** |

## 8. 风险与应对

| 风险 | 影响 | 应对策略 |
|------|------|----------|
| Java 复杂业务逻辑迁移遗漏 | 功能回归 | 每批迁移后补充集成测试，对照原 Java 接口响应逐字段校验 |
| fastapi-users 无法满足定制认证需求 | 登录/权限流程变更 | 提前验证 `fastapi-users` 的自定义策略（Transport/Strategy），必要时保留手写 JWT 逻辑 |
| 前端团队不熟悉 OpenAPI 生成工作流 | 协作摩擦 | 将 `openapi-typescript` 写入 `package.json` 的 `generate` 脚本，每次后端更新后一键执行 |
| 性能担忧（Python vs Java） | 高并发场景 | FastAPI + asyncpg 在 IO 密集型场景表现优秀；CPU 密集型任务（如音频处理）可保留独立服务或移至 Celery |

## 9. 结论

- **后端**：用 FastAPI + SQLAlchemy 2.0 + fastapi-users 统一替换 Java，预计减少近一半后端代码。
- **前端**：不迁移框架，通过 `unplugin-auto-import`、`unplugin-vue-components`、`openapi-typescript` 三大工具消除样板代码和手写 API 层。
- **整体**：从三模块异构（Java + Python + Vue）压缩为两模块同构（Python + Vue），代码总量预计从 **~41,000 行** 降至 **~30,000 行** 左右，维护成本显著降低。
